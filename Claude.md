# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TravelObligator is an AI travel **decision** platform, not a one-shot itinerary generator. The product is the staged decision pipeline that produces and explains a plan, not just the plan itself:

```text
Traveler Profile → Destination Context → Trip Strategy → Stay + Transport
  → Experience Planner → Plan Validator → Feedback Pipeline → Final Itinerary
```

Two services: a FastAPI/Python backend (`backend/`) and a Next.js/React frontend (`frontend/`), backed by PostgreSQL by default (Section 200A; an explicit Local JSON fallback exists for dev/test — see Architecture below).

**V1 is released and deployed** (single-city planning): frontend `https://travelobligator.vercel.app` (Vercel) → same-origin `/api/*` rewrite → Render FastAPI backend → Neon PostgreSQL + Upstash Redis. `docs/23_v1_release_reference.md` is the current-state reference (scope, production topology, evaluation results, limitations); `docs/22_free_tier_deployment.md` is the deployment contract and verification record.

Read `docs/23_v1_release_reference.md`, `docs/00_product_vision.md` and `docs/09_planning_state.md` first if you haven't touched this repo before. The numbered documents `docs/00`–`docs/21` describe the design as it evolved; `README.md` links the main ones.

## Commands

**Backend** (from `backend/`, or via Docker):
```bash
pip install -r requirements.txt -r requirements-dev.txt   # requirements-dev adds pytest
uvicorn app.main:app --reload                              # dev server, port 8000
```

**Tests** (from repo root — `pytest.ini` sets `pythonpath=backend`, `testpaths=backend/app/tests`):
```bash
pytest                                                      # full backend suite
pytest backend/app/tests/services/test_feedback_service.py  # one file
pytest backend/app/tests/services/test_feedback_service.py::test_name  # one test
python -m compileall backend/app                            # compile check (CI also runs this)
```
Ordinary pytest skips the project `.env`, but inherited OS environment variables still take precedence. If the shell previously exported live provider/config variables, run configuration/default tests from a clean environment.

There is no backend lint/type-check config (no ruff/mypy) in this repo.

**Frontend** (from `frontend/`):
```bash
npm run dev      # dev server, port 3000
npm run build    # next build
npm run lint     # eslint; CI also runs `npx tsc --noEmit` and the build
npm test         # Node's built-in test runner over frontend/tests/*.test.mjs (no test framework dependency)
```

**Full stack**: `docker compose up --build` (root `docker-compose.yml`, Section 200E) is a production-style stack from the real images: `postgres` → one-shot `migrate` (`alembic upgrade head`; the backend never migrates) → `backend` (one Uvicorn worker, read-only root, `127.0.0.1:8000`) → `frontend` (Next standalone, `127.0.0.1:3000`), plus a `redis` cache-only, DISPOSABLE container that is NOT a backend startup dependency (the backend must start degraded without it; PostgreSQL + the migration are the only hard prerequisites); Postgres/Redis publish no host ports and require `POSTGRES_PASSWORD` + `SESSION_SECRET_KEY` from your environment (no defaults). The hot-reload dev workflow is `docker compose -f docker-compose.yml -f docker-compose.dev.yml up`.

CI (`.github/workflows/ci.yml`, Section 203A) runs six jobs on Python 3.11 / Node 22 / PostgreSQL 16 / Redis 7.4: `Backend / Hermetic` (`compileall` + plain `pytest`, no services), `Backend / Integration` (single Alembic head, `alembic upgrade head` on an empty database, full suite with both gates, zero skips enforced; includes the backup / restore / rollback drill, which needs `pg_dump` / `pg_restore`), `Frontend / Build` (`npm ci`, `tsc --noEmit`, lint, unit tests, build, `npm run check:headers`), `Browser / E2E` (Playwright/Chromium against the production frontend build and the offline backend of `backend/scripts/e2e_backend.py`; no service, database, provider key or secret; a skipped test fails the job — `frontend/e2e/README.md`), `Containers / Build & Smoke` (production images, `scripts/ci/image_audit.sh`, Trivy image gate, `scripts/ci/container_smoke.sh`) and `Security / Scan` (Trivy secrets + dependencies). Job names are branch-protection check names — don't rename them. No deploy step, no registry push, no secret. A separate workflow, `.github/workflows/uptime.yml`, is not CI: it GETs the public frontend page on a schedule (never the backend unless explicitly switched on — it is not a keepalive) and is never a required check.

**Browser tests** (from `frontend/`): `npm run e2e` builds the production app, starts it and the offline backend, and runs every viewport (`npx playwright install chromium` once); `npm run e2e -- --project=desktop` for one. They automate Chromium only and measure geometry and axe-detectable problems — never cite them as WCAG conformance, as screen-reader, real-device, Safari/Firefox or real-map-tile verification. A reported, unfixed application defect is a test named `DEFECT <id>` marked `test.fail()`; never skip, weaken or retry a test to make the suite pass (`retries: 0`).

**Limited beta copy** (`frontend/lib/beta-notice.ts`, `frontend/app/BetaNotice.tsx`): the first release is a labelled limited beta. The label and its five points are shown, as visible text, on the sign-in screen and the signed-in page; they are general copy and never replace, soften or duplicate an itinerary's own validation banner. Never write copy that calls itineraries in general complete, verified, guaranteed or ready to follow. The registration form shows `PASSWORD_LOSS_WARNING` and the privacy notice repeats it word for word (a test keeps them identical): there is no password recovery and no way to verify ownership without the password, so nothing may promise a reset, and an operator-performed deletion exists only as the mailbox-challenge procedure of runbook section 8.1 (owner decisions D3a–D3c: contact `garimaprachi2411@gmail.com`, a code sent TO the account's address, deletion only by `backend/scripts/locked_out_account_deletion.py`) — never describe any shortcut (an email address, a message "from" the address, trip details) as enough. The privacy notice tells five kinds of copy apart (the app's own database, the automated daily backups, exports kept by the operator, hosting-provider backups and logs, what was sent to external services) and states no retention period for operator exports until one is really in force.

**Operations** (`docs/25_operations_runbook.md` — backup/restore, deployment order, rollback, monitoring, incident checklist): the backend starts only on a database at EXACTLY its own Alembic head, so code and schema always move together and a code rollback across a migration needs an explicit, manual `alembic downgrade` first — never automate one. Keep migrations additive (tables, indexes, nullable columns): `tests/scripts/test_operations_p1d.py` fails on anything else after production's revision, and the runbook's rollback section must be rewritten before such a migration ships. The three operator scripts are manual and read their database from their OWN variables, never `DATABASE_URL`: `backend/scripts/db_backup_restore.py` (`backup` / `restore` / `verify`: a restore goes only into a database with NO object in any schema, needs the dump's manifest and `--confirm-empty-target <name>`, refuses the backup source and `DATABASE_URL` by text and by asking the servers, refuses when it cannot tell, and rejects a copy that does not match the manifest — never weaken one of these, never add `--clean`, and never claim the tool can tell which database is production: isolating the target is the operator's documented step), `backend/scripts/ops_report.py` (read-only alert conditions from the database) and `backend/scripts/public_check.py` (GET-only availability check). None may print a connection string, an email address, an id or itinerary text; a backup is personal data and never goes in the repository. Two kinds of operator-held copy are told apart: the automated daily backups (GitHub Actions on `main` → GnuPG-encrypted → S3 `neon/`, expiring after 7 days; runbook 2.6) are the ONLY copy for which the privacy notice states a period ("about seven days", kept in step with runbook 2.6 by tests), and the notice must never say that deleting a trip or account removes backups; manual exports have NO retention policy in force (30 days is a recommendation pending verified storage, access, encryption and deletion), so do not state one for them anywhere. After a migration that adds a table, grant the backup role SELECT on it (runbook 2.6). A fourth, manual operator command, `backend/scripts/locked_out_account_deletion.py` (`challenge` / `verify` / `status` / `delete`), deletes a locked-out user's account only after a verified mailbox challenge (runbook 8.1): its own variables `ACCOUNT_DELETION_DATABASE_URL` / `ACCOUNT_DELETION_SESSION_SECRET_KEY`, never `.env` or `DATABASE_URL`; an operator-local challenge store holding only hashes (code: scrypt; account id and address: keyed HMAC), 72 hours at most, five attempts, single use; deletion only through `data_deletion_service.delete_account`, never SQL; output names an account only by fingerprint. Never weaken one of these checks, never expose it over HTTP, and never run it on production in a test. Rolling the backend back across the P0/P1-A migrations drops the quota-accounting tables and reinstates code with no cost limits — fix forward when feasible, and otherwise keep public generation disabled until the limits are back (runbook 4.3). The scheduled backend check of `uptime.yml` stays off by the owner's decision; never add anything that keeps the free-tier backend awake. A table added later must be added to `APPLICATION_TABLES` in the backup tool as well as to the deletion service.

## Architecture

**`PlanningState` is the single source of truth.** It's one Pydantic model (`backend/app/models/planning_state.py`) holding every section of a trip's plan (traveler profile, destination context, trip strategy, stay/transport, experience plan, validation report, feedback history, locks, version history, provider coverage, etc.). Each section is owned by exactly one backend stage service; the frontend renders directly from it and invents nothing itself.

**Backend layering** (`API → Orchestrator/Services → ProviderGateway/Repositories/Validators → Provider Adapters/Database`):
- `backend/app/api/routes/trips.py` — the single router (prefix `/trips`). Every response is wrapped in a standard envelope (`success`, `data`, `message`, `errors`, `metadata`) built in `core/response.py`; business errors are `AppError` subclasses from `core/errors.py`, converted to that envelope by a handler in `main.py`.
- `backend/app/services/planning_orchestrator.py` — `PlanningOrchestrator.generate_full_plan()` runs the 6 core stage services in a fixed order inside `POST /trips/{id}/generate`, saving `PlanningState` to the repository after every stage. This is the legacy engine; the default is the LangGraph engine (`PLANNING_ENGINE_MODE=langgraph`) over the same stage services. Generation is a single synchronous request by default and a polled background job (HTTP 202, `BackgroundTasks` + database leases — not a durable queue) with `ASYNC_GENERATION_ENABLED=true`, which production sets.
- Stage services (`backend/app/services/{traveler_profile,destination_context,trip_strategy,stay_transport,experience_planner,plan_validator}_service.py`) each own specific `PlanningState` fields and must not touch fields owned by another stage.
- `backend/app/providers/gateway.py` (`ProviderGateway`) is the *only* way stage services reach external data — never import a provider adapter directly. **Production uses Geoapify for geocoding, places and routing (see "Final V1 itinerary engine" below); Overpass, Nominatim and OSRM are development-only.** Real adapters exist for places (OpenStreetMap/Overpass for POI discovery in development, Geoapify Places in production; destination geocoding and named-place search go through a separate `GeocodingProvider` in `app/providers/geocoding/` selected by `GEOCODING_PROVIDER` — `nominatim` default for dev/tests, paced to 1 req/s with a 429 cooldown; `geoapify` in production, needs `GEOAPIFY_API_KEY`; no fallback between them, and `APP_ENV=production` rejects the public Nominatim endpoint — Section 203C.1), weather (Open-Meteo), holidays (Nager.Date), currency (Frankfurter), routing (OSRM — `ROUTING_PROVIDER` default `not_connected`, `osrm` when explicitly configured, `geoapify` in production), and accommodation/flights (`scraped_local` — a local/manual static-HTML parser, enabled by default but honestly `unavailable` with no file present at `SCRAPED_ACCOMMODATION_HTML_PATH`/`SCRAPED_FLIGHT_HTML_PATH`). Flights additionally has a real, live third-party adapter (Kiwi via MCP — `FLIGHT_PROVIDER=kiwi_mcp` + `KIWI_MCP_ENABLED=true`, both required, default off). Transit still has no adapter and always reports `not_connected`. Hotel ratings (`HOTEL_RATINGS_PROVIDER`) has a provider slot but no live rating source wired in yet, defaulting to `not_connected`.
- `backend/app/repositories/` — **Section 200A: PostgreSQL is the default persistence backend.** `Settings.persistence_backend` (`PERSISTENCE_BACKEND`, default `postgres`) is the one selector; `app/repositories/factory.py` (`get_*_repository()`) returns Postgres repositories for users, trips, planning states, jobs and branches/revisions (SQLAlchemy/psycopg, Alembic migrations run as a release step, never automatically). `DATABASE_URL` is required (no default); missing/invalid/unreachable/un-migrated Postgres stops startup with a credential-free message and **never falls back to Local JSON**. `PERSISTENCE_BACKEND=local_json` is an explicit dev/test fallback (`LocalJsonStore` → gitignored `backend/.data/travelobligator_state.json`); hermetic pytest selects it explicitly in `conftest.py`. Never bind a Local JSON repository singleton directly in a service — always resolve through the factory.
- **Containers and runtime (Section 200E).** `docker compose up --build` is a production-STYLE stack from the real images (`postgres` → one-shot `migrate` → `backend` → `frontend`, plus `redis`); `docker-compose.dev.yml` is the old hot-reload workflow. Backend: multi-stage `python:3.11.18-slim-bookworm`, non-root uid 10001, exec-form `python -m app.serve` = **exactly ONE Uvicorn worker per container** (metrics/heartbeats are process-local; scale by containers), read-only root + tmpfs in PostgreSQL+Redis mode. **Migrations are an explicit step, never run by the web process** (the backend only verifies the head and refuses to start on a mismatch). DB pool/timeouts are settings (`DB_POOL_SIZE`+`DB_MAX_OVERFLOW` = max connections per container; `DB_STATEMENT_TIMEOUT_MS`/`DB_LOCK_TIMEOUT_MS` apply to request traffic, not migrations). Graceful SIGTERM closes this process's own in-flight jobs as `JOB_INTERRUPTED` (lease-conditional) and exits; a hard kill relies on lease expiry. Postgres/Redis publish NO host ports (dev override: 127.0.0.1 only); `/health` is the container liveness check, `/ready` is for traffic routing; `/ready` and `/metrics` are operational endpoints; in production they are protected by `OPS_TOKEN` and return 404 without valid access. Frontend: Next `output: "standalone"`, Node 22, non-root; the browser's API URL is the RUNTIME `API_BASE_URL` (never an internal service name). Async jobs are `BackgroundTasks` + leases, **not a durable queue**. Details: `docs/14_backend_architecture.md` section 164.
- **Health, readiness, observability (Section 200D).** `/health` is liveness ONLY (no dependency call, no config dump); `/ready` (`core/readiness.py`) = PostgreSQL reachable + schema at the code's Alembic head (else 503 `not_ready`), Redis down = `degraded` (200), Redis disabled reported as such, external travel/AI providers are NEVER called by readiness. Probes are bounded (`READINESS_TIMEOUT_SECONDS`, dedicated one-connection engine, `DB_CONNECT_TIMEOUT_SECONDS`) and recover without a restart. Metrics: `core/metrics.py` (dependency-free registry, Prometheus text at `/metrics`, `METRICS_ENABLED`); **never label a metric with a trip/job/user/revision id, destination, free text, URL or request id** (HTTP uses route TEMPLATES). Logging: use the existing allowlisted structured pipeline + `core/ops_events.py` names; every line is passed through `core/redaction.py`; never log feedback text, itinerary/narrative text, prompts, provider payloads, tokens or URLs. `validate_runtime_configuration` rejects contradictions at startup (e.g. job max > 1 with PostgreSQL). Heartbeat threads are registered and stopped at shutdown. Details: `docs/14_backend_architecture.md` section 163.
- **Transactions and concurrency (Section 200C).** PostgreSQL is authoritative and does the concurrency control; Redis is never a lock. Use `app/repositories/unit_of_work.py` (`unit_of_work()` / `run_atomic`) for multi-write transitions: repositories bound to its one session never commit themselves; **never call a provider/AI/Redis inside a unit of work** (compute first, then a short transaction). `PlanningState` writes are optimistic: `planning_states.lock_version` compare-and-set via a private `_lock_version` token (stale writer → `ConcurrentStateUpdateError` → HTTP 409 `CONCURRENT_UPDATE`; an unread object may only INSERT). State + revision + branch head commit together through `RevisionLineageService.commit_state_with_revision` — never pair `save()` with `record_current_revision()`. Branch activation locks the state row; branch heads use compare-and-set. Jobs: a partial unique index allows one queued/running job per trip; running jobs are owned by a DB lease (`claim`/`heartbeat`/`transition`, `GENERATION_JOB_LEASE_SECONDS`); terminal transitions are conditional and idempotent; startup recovery only closes expired leases. Isolation is READ COMMITTED (not SERIALIZABLE); only 40001/40P01 are retried (3 attempts). Local JSON stays an explicit dev backend **without** these guarantees. Not exactly-once distributed execution. Details: `docs/14_backend_architecture.md` section 162.
- **Provider-response cache (Section 200B).** `PROVIDER_CACHE_BACKEND` (default `redis`; `sqlite` is the explicit local-dev alternative; `PROVIDER_CACHE_ENABLED=false` is the kill switch) picks the backend inside `get_provider_cache_store` (`app/storage/provider_cache_store.py`); the Redis implementation is `app/storage/redis_provider_cache_store.py` (keys `<prefix>:provider-cache:v1:<provider>:<sha256>`, JSON envelope, volatility-based TTLs, bump `CACHE_NAMESPACE_VERSION` to invalidate). **Redis is an optimization, never authoritative:** if it is down, provider calls simply run uncached — never a hidden SQLite fallback, never a fabricated value, never a failed request. A malformed `REDIS_URL` stops startup; an unreachable one only degrades. Never cache AI/LLM output or transient provider failures; scraped/local-file caches stay off Redis. Ordinary `pytest` selects `sqlite` explicitly and needs no Redis; real-Redis tests are gated (`TRAVELOB_RUN_REDIS_TESTS=1` + `REDIS_URL`, marker `redis_integration`). Details: `docs/14_backend_architecture.md` section 161.
- **Free-tier deployment contract (Section 203B; deployed in 203C, production acceptance done in 203D; production now runs the restricted M1 deployment of `b559ff0` on schema `a94c0e7d2b61`, where cold-start recovery after a genuine free-tier idle sleep PASSED — `docs/22` section 14.1. The separate manual cold-start check from a phone, `docs/28` section 3, is still pending).** Topology: Vercel (frontend) → same-origin `/api/*` rewrite → Render free Docker web service → Neon PostgreSQL + Upstash Redis. The rewrite exists only when `BACKEND_ORIGIN` is set at frontend build time (`frontend/next.config.ts`; pair with runtime `API_BASE_URL=/api`); local dev, Docker and CI leave it unset. `APP_ENV=production` turns on strict startup validation in `core/operational_config.py` (PostgreSQL only, no SQLite provider cache, `APP_DEBUG=false`, Secure/HttpOnly/non-`none` session cookie, ≥32-char `SESSION_SECRET_KEY`, https-only explicit CORS origins); a wildcard or credentialed CORS origin is rejected in every environment. Every backend response is `Cache-Control: no-store` (`core/no_store_middleware.py`). `/health` is always public; `/ready` and `/metrics` require `Authorization: Bearer <OPS_TOKEN>` when `OPS_TOKEN` is set, are 404 in production without it, and stay open otherwise (Compose/CI). `render.yaml` is one free web service with no secret values; migrations stay a manual step before each deploy. No keepalive/cron ping to defeat free-tier sleep. Details, the deployment checklist and the production verification record: `docs/22_free_tier_deployment.md`.
- **Final V1 itinerary engine (Section 203C.2B).** Production topology: Geoapify Geocoding (destination + named-place grounding) → Geoapify Places (`PLACES_PROVIDER=geoapify`, `providers/places/geoapify_places_adapter.py`: broad factual pool inside the destination boundary, category identifiers only from the verified snapshot in `geoapify_categories.py`) → Groq anchor proposals (hypotheses only; every one is grounded through the geocoder before it is eligible, and a grounded place already in the pool keeps the pool identity) → candidate quality → inventory sufficiency gate → reasoning → Geoapify Routing (`ROUTING_PROVIDER=geoapify`) → validation → narrator. **Overpass is development-only** (`PLACES_PROVIDER=openstreetmap`, rejected with `APP_ENV=production`); never add a fallback between providers. **Provider result order is never a prominence signal.** `T = days × pace target (2/3/4)`, `R = ceil(0.8·T)`, `H = ceil(2.25·T)` live in `services/pace_targets.py`; `services/usefulness_contract.py` owns the semantics: `viable ≥ H` healthy, `≥ T` sufficient, `≥ R` thin-but-usable, `< R` insufficient. Whenever `viable ≥ R` a plan needs ≥ R meaningful stops and no empty day (one AI repair, then one deterministic top-up, then `UNDERFILLED_PLAN` / needs_review). **Only `viable < R` is `INSUFFICIENT_VERIFIED_INVENTORY`, and that is a completed generation with `readiness=blocked` (job `succeeded`, state persisted) — never an `AppError` or a failed job, and never padded.** Routing is bounded and non-quadratic: one multi-waypoint request per day, at most one alternative order per day (chosen by `services/day_order_heuristics.py`; the routing services themselves never compute straight-line distance), no pair matrix. **Provider credits are accounted per generation** through an explicit `GenerationProviderContext` (`core/provider_usage.py`) passed from each entry point into `gateway.places_for(ctx)` / `routing_for(ctx)` / `get_route_sequence(..., ctx)` — never a process-global counter; adapters reserve before a request, settle after, and refuse locally past `GEOAPIFY_MAX_CREDITS_PER_GENERATION`. Every Geoapify call goes through `providers/geoapify_client.py` (generic `ProviderRequestError`; `GeocoderError` is only its geocoder-worded subclass). The hermetic suite turns the gate off for its tiny legacy fixtures (`INVENTORY_SUFFICIENCY_GATE_ENABLED=false` in `conftest.py`); opt in with the `inventory_sufficiency_gate_enabled` fixture. Benchmark data (`backend/scripts/benchmark/`) is never imported by `backend/app`, and no city or landmark name belongs in production logic. Details: `docs/22_free_tier_deployment.md`.
- **Generation latency: profiling, bounded I/O concurrency, model-stage budgets (Sections 1A–1C).** Measurement and latency only — none of this may change which plan is produced.
  - *Profiling (1A).* `core/performance.py`: one `PerformanceRecorder` per generation, bound by a context variable (never a process global), written to `PlanningState.generation_performance_report` (optional; numbers under fixed lower-case keys only — never a query, URL, key, prompt, model output or place name). Stage times are exclusive and add up to the total; time spent inside concurrent tasks is kept apart (`stage_task_ms`). The report is attached BEFORE the final commit and never touched afterwards (the committed state must equal its revision); `backend/scripts/canary_city.py` owns its own recorder for complete figures. Every recorder call is a guarded no-op: timing can never fail a generation. Performance is reported, never an acceptance check.
  - *Bounded concurrency (1B).* `core/bounded_concurrency.run_bounded` runs INDEPENDENT provider requests on a small short-lived thread pool (the clients are synchronous) and returns outcomes in TASK order. The rule for every batch is **plan on the calling thread (cache check, allowance taken in order) → fetch concurrently → apply on the calling thread in the original order**; a task only fetches and never touches shared generation state. Batches: broad Places (`search_broad_inventory`), anchor / must-visit named lookups (`search_must_visit_places`; the anchor reserve runs as later batches that dispatch exactly what a one-at-a-time loop would), Place Details, the two lookups of one suspect identity pair, day walking routes, drive legs (only after every walking leg is known), weather/holiday/currency. `PROVIDER_IO_CONCURRENCY_ENABLED=false` runs the same tasks serially and must give the SAME plan. Provider credits are reserved atomically by the usage tracker at request time (never oversubscribed).
  - *Geoapify limits (1B/1C).* A request takes a slot of the generation's limiter (`GEOAPIFY_MAX_CONCURRENT_REQUESTS`, 1–4, default 4 — do not raise it) and then of the process limiter (`GEOAPIFY_PROCESS_MAX_CONCURRENT_REQUESTS`, default 6), always in that order, released in `finally`. Both are in-process (`core/provider_usage.py`); the process limit bounds ONE container, not a multi-container deployment. Never Redis/PostgreSQL.
  - *Model-stage budgets (1C).* `providers/ai_stage_budget.StageRun`: each generation-time Groq stage (anchor proposal, itinerary reasoning, itinerary repair, narrator) has ONE total wall-clock budget (`GROQ_{ANCHOR,REASONING,REPAIR,NARRATOR}_TOTAL_BUDGET_SECONDS` = 25/20/20/25; monotonic; 0 disables) covering every attempt, the structural retry and the backoff. The SDK's own retries are OFF (`max_retries=0`); a stage makes at most ONE recovery attempt — structural (anchor, narrator) OR transport (rate limit / timeout / 5xx, `GROQ_MAX_RETRIES`, default 1) — so at most 2 requests, never a product. An attempt's timeout is `min(per-request timeout, budget left)`; a retry is not started with under 3 s left. Running out is `deadline_exceeded` (a latency outcome, never a factual one) and the existing deterministic fallback takes over; never fabricate to fill the gap. Never retry schema-invalid output or a validation rejection at the transport level, and never add a retry layer above or below this one.
  - *Also.* Nager.Date HTTP 204 / empty body is `unavailable` with `failure_reason="holiday_data_not_provided"` (not a failure, not "no holidays"), remembered for `NAGER_DATE_NO_DATA_CACHE_TTL_SECONDS`. The gateway logs `provider=… operation=… status=…`; an optional inventory provider (accommodation, flights) with nothing to offer is INFO (`provider.no_data`), real failures stay WARNING. All of these settings are in `.env.example`.
- **Groq ↔ Gemini LLM resilience group.** Infrastructure only — it may never change planner logic, and Gemini is never a factual source (same grounded input as Groq, no `tools` / Google Search / Maps grounding, model name only from `GEMINI_MODEL`, never hardcoded).
  - *Who is routed.* Only a stage that is already enabled and whose own selector is `groq` or `gemini` (`AI_CANDIDATE_PROPOSAL_PROVIDER`, `AI_ITINERARY_REASONING_PROVIDER` — also repair — and `ITINERARY_NARRATOR_PROVIDER`). A disabled stage, `not_connected` and `anthropic` are never routed, whatever keys exist; the Anthropic adapters are untouched. With `LLM_FAILOVER_ENABLED=true` and both providers configured (Groq: `GROQ_API_KEY`; Gemini: `GEMINI_API_KEY` + `GEMINI_MODEL`) the order is `LLM_PRIMARY_PROVIDER` then `LLM_SECONDARY_PROVIDER`; with one configured, or failover off, the stage is single-provider and behaves as before (including the historical `GROQ_MAX_RETRIES`).
  - *One stage adapter, two clients.* The `Groq*Provider` stage classes are the routed adapters (`gemini_adapter.py` in each package is a selector subclass that overrides nothing). `providers/llm_structured_clients.py` gives both providers the same `.invoke(prompt)` returning the stage's own wire schema, so everything after the call (reference resolution, per-item validation, grounding, sanitizing) is one code path. Never add a Gemini-specific result model or relax a check for one provider.
  - *Budget.* `ai_stage_budget.StageRun` is still the only retry layer (`enable_failover` / `allow_failover`). A routed stage makes at most **two** provider requests under the same wall-clock budget (the clock is never reset; no request starts with under 3 s left). The second request is ONE of: the other provider (after a transport failure if it is callable; after a malformed / schema-invalid answer only if it is HEALTHY) or the stage's own structural retry (anchor, narrator only). Two is a maximum, not a quota: a transport failure opens that provider's circuit first, and if no other provider is then eligible the stage goes straight to its deterministic fallback — a routed stage never retries the provider that just failed (the same-provider transport retry exists only on the single-provider path). An answer that parsed and was then rejected by application validation or grounding never triggers a second request. Both SDKs' own retries are off (`max_retries=0`, `HttpRetryOptions(attempts=1)`).

A completed request makes the provider HEALTHY even if its answer is structurally invalid (`json_validate_failed` is not a provider failure). HALF_OPEN allows one probe at a time. DRAINING comes only from quota evidence: Groq's `x-ratelimit-*` headers (read by an httpx response hook; only six numbers are kept) or optional `GEMINI_{RPM,TPM,RPD}_LIMIT` against local counters — never from latency or a guess.

- **Day composition is one shared objective, separate from usefulness (Q3).** `services/day_composition.py` (pure: no provider, routing or model call, no destination name) decides which eligible places share a day; it reads each candidate's Q2 `preference`/`tail` and never changes that ordering. Hard rules make a move inadmissible (removing a grounded must-visit, a place that may not enter, two of one conflict group, a plan class cap, more hard market excess, taking the only cover of a requested interest, creating a dispersed day). A model's plan keeps its places where feasible (regrouping still obeys `AI_DAY_SPATIAL_REGROUPING_ENABLED`; a replacement needs `viable ≥ T`, no active lock, at most one per trip day). The reasoning bound's step E is area-aware (companions ≤ half its space, then one alternative per other area ≤ half the rest, then usefulness; A–D untouched); candidate lines carry `area=`, a block lists each area's size and near areas, no coordinate/distance/duration is sent, and an area id is scrubbed from model prose. Never add a second composition objective, a pairing table of categories, a locality name, or a routing call here.

Password reset does not exist; a locked-out user's deletion is the runbook 8.1 procedure, whose prerequisites (runbook 8.2, including a rehearsal) must be done before the release that publishes it.

HSTS is opt-in (`FRONTEND_HSTS_MAX_AGE_SECONDS`, build time) and only for a hostname the project controls. **A proxied `/api` response is NOT decorated by `next.config.ts` headers on Next's own server** (measured), so API responses are protected by the backend itself: `core/security_headers_middleware.py` (with `no_store_middleware`) sets `nosniff`, `X-Frame-Options`, `Referrer-Policy: no-referrer` and an ENFORCED `default-src 'none'; frame-ancestors 'none'` on every response except the dev-only `/docs` and `/redoc` pages; a new backend response path needs nothing extra, and never move these to the proxy. `npm run check:headers` builds against a stub backend and checks the real production server (headers, proxy pass-through, no secret in browser assets). *Configuration:* `render.yaml` is the complete non-secret production configuration, including the model stages the quality evaluation ran with (reasoning, repair, narrator, `GROQ_MODEL`, `GEMINI_MODEL`, failover); only credentials and the CORS origin are dashboard values (`sync: false`), and `tests/core/test_production_completeness_p1b.py` builds settings from the file and validates them — add a production setting there, not only in a dashboard. With `APP_ENV=production` startup refuses (naming the variable, never a value) when a release model stage is off (`PRODUCTION_ALLOW_AI_STAGES_DISABLED=true` is the explicit opt-out), a switched-on stage has `not_connected`, a selected provider lacks its key/model, or `LLM_FAILOVER_ENABLED=true` with only one of Groq/Gemini configured. That is presence only — never call a provider at startup. Do not put quality-phase switches or planner/routing/model budgets in `render.yaml`: they stay at the code defaults that were evaluated.
- **Final Batch 2 reliability closure (`docs/36_final_batch2_reliability.md`).** With `APP_ENV=production` startup refuses an integration the release was not evaluated with — `TARGETED_REGENERATION_ENABLED`, `AI_FEEDBACK_INTERPRETER_ENABLED`, `FLIGHT_PROVIDER=kiwi_mcp`/`KIWI_MCP_ENABLED`, `FLIGHT_AIRPORT_LOOKUP_PROVIDER` — unless `PRODUCTION_ALLOW_UNEVALUATED_INTEGRATIONS` names it (`targeted_regeneration`, `feedback_interpreter`, `kiwi_flights`, `airport_lookup`; an unknown name is refused; it relaxes nothing else); `render.yaml` pins them and the manual-file providers off. **No user action may change saved itinerary content without its revision** (`tests/api/test_revision_integrity_batch2.py`): `POST /generate` builds a FIRST plan only (409 `PLAN_ALREADY_GENERATED` once `generation_job_service.has_usable_generated_plan`; a failed/interrupted/unresolved/unusable one may be retried), and `POST /ai-candidate-promotions` is development-only (404 in production; `promotion_refresh_available` tells the client). "Keep this place" is offered only when `change_requests_applicable !== false`; a stored keep stays visible and removable; never word a keep as preserving a place (an active keep blocks applying changes). `.env.example` must list every setting (`test_env_example_sync.py`), and every field `types.ts` declares on a backend-named type must exist on that model (`test_frontend_types_contract.py`).
- **Final quality acceptance (`docs/37_final_quality_acceptance_v3.md`).** `quality-holdout-v3` (`backend/scripts/benchmark/quality_v3.json`) is FROZEN and UNSEEN, with a frozen protocol (`evaluation/quality_v3/protocol.json`: set digest, base commit, source fingerprint, configuration digest, trip date and execution window, request limits, interruption rule, review and acceptance rules), both pinned in `tests/scripts/test_quality_acceptance_v3.py`. It runs only through `scripts/quality_acceptance_v3.py` (whole set, once, refused unless every preflight check passes); `benchmark_quality.py`, the canary and every verification script refuse it. Protocol version 2 (amendment record `evaluation/quality_v3/AMENDMENT_v2.md`): every attempt has write-once records, cumulative limits (12 attempts) are enforced across resumes, every step is entered in a hash-chained audit log beside the result folders, the reviewer (never the operator) signs a locked independence declaration before any packet exists, and the scoresheet is locked by `submit` before anything is unblinded — never weaken, bypass or hand-repair any of these. Never run, sample, canary or tune on one of its destinations; never name one in code, a test or a fixture. Any edit to `backend/app` (outside tests), `backend/scripts` or `backend/requirements.txt` changes the frozen fingerprint: before the run that is a recorded protocol amendment (doc 37 section 10), after the run it is never allowed. The result is recorded as it comes out and never rerun or re-scored.
- Authentication exists (Section 184): `/auth/*` routes (`backend/app/api/routes/auth.py`), a signed HttpOnly session cookie (`backend/app/auth/sessions.py`), and every `/trips/*` route requires a logged-in user and checks trip ownership (`backend/app/auth/dependencies.py`, `backend/app/auth/ownership.py`, `TripRecord.owner_id`). Knowing a `trip_id` is not enough to read a trip.
- Services, the orchestrator, and the gateway are constructed as module-level singletons at import time, not via FastAPI `Depends()` — tests override behavior by monkeypatching these singletons directly (see `backend/app/tests/conftest.py`).

**Regeneration is implemented, but MVP-scoped and refusal-first.** `POST /trips/{id}/regenerate` (Section 174) mutates the plan only when `confirm: true`, at least one feedback event is still pending, zero locks are active, and a real affected stage is derivable from that feedback — in that case it reruns exactly those stages via `PlanningOrchestrator.rerun_affected_stages`, creates a new `VersionHistoryItem`, and marks the feedback events applied. Every other case (missing/false `confirm`, any active lock, no pending feedback, or no derivable affected stage) is a distinct, named refusal (`REGENERATION_NOT_AVAILABLE` / `REGENERATION_BLOCKED_BY_LOCKS` / `REGENERATION_NO_PENDING_FEEDBACK`) that appends an audit attempt and changes nothing. An active lock always blocks regeneration outright — the system never works around a lock, merges past it, or "preserves" it by excluding just that item; a locked plan must be unlocked first. A successful regeneration is never a claim that the plan improved, and never a claim it is now ready for real-world use without further review. `POST /trips/{id}/feedback` still only classifies feedback with deterministic keyword rules (no AI, no plan mutation itself) — `POST /trips/{id}/regenerate` is the endpoint that can act on it. Before touching any regeneration-adjacent code, read `docs/17_regeneration_manual_qa.md` and run its checklist — every refusal path above is a safety contract, not a placeholder to "finish." **Section 202B.1 (honest semantics):** the legacy (non-targeted) path only reruns deterministic stages over the same `trip_request` — no stage reads feedback text — so it can no longer claim a free-text request was applied. Legacy regeneration now runs only for a `feedback_type` with a registered deterministic operation *and* a postcondition proving the effect (`LEGACY_SUPPORTED_OPERATIONS` in `regeneration_mutation_service.py`, intentionally empty); otherwise it refuses with `REGENERATION_FEEDBACK_NOT_INTERPRETABLE` (no rerun, no version, feedback stays pending). Free-text changes need the targeted AI path (`TARGETED_REGENERATION_ENABLED=true` + AI feedback interpreter). A targeted result that changes nothing is `REGENERATION_NO_EFFECT` (no version); reported affected/preserved days are derived from the final states, never from plan metadata; AI provider failures are classified (`app/providers/ai_failure.py`) into `REGENERATION_PROVIDER_RATE_LIMITED` / `REGENERATION_AI_UNAVAILABLE`, never the generic refusal. Provider-grounded experiences carry `provider_source`/`provider_place_id` and a deterministic `experience_id`, so unchanged places keep their id across regenerations and the same place is never scheduled twice.

**AI candidate-proposal subsystem** (`backend/app/providers/ai_candidate_proposal/`) has two uses (`AI_CANDIDATE_PROPOSAL_PROVIDER` default `not_connected`; adapters exist for `anthropic`, `groq` and `gemini` — none is a factual data source, all propose candidates only, with a schema that structurally forbids factual fields like price/rating/coordinates). **Live, in production:** `AI_CANDIDATE_PROPOSAL_PROVIDER=groq` (Gemini failover) with `AI_CANDIDATE_DISCOVERY_ENABLED=true` produces the anchor proposals of the Final V1 itinerary engine, each grounded through the geocoder before it is eligible. **Shadow mode:** `AI_CANDIDATE_DISCOVERY_SHADOW_MODE_ENABLED` (default off) populates `ai_candidate_proposal_batch`/`candidate_grounding_batch` for inspection only — it never feeds scheduling, `validation_report`, or `provider_coverage`. Don't change how either path feeds the real pipeline unless explicitly asked to.

**Frontend** is a single route (`frontend/app/page.tsx`, one large file — no `components/`/`hooks/`/dynamic routing). `frontend/lib/api.ts` is a thin fetch client, one function per backend endpoint; `frontend/lib/types.ts` is a hand-maintained partial mirror of backend response shapes (not generated — keep both in sync manually when changing API contracts). State is plain `useState`, no store library. Loading a trip fires `GET /summary` then 7 parallel calls assembled client-side into one `PlanResult` — this deviates from `docs/16_frontend_architecture.md`'s single-fetch design; that's a known, accepted divergence, not a bug to silently "fix."

**Next.js version note**: `frontend/AGENTS.md` (pulled in via `frontend/CLAUDE.md`) warns this is a bleeding-edge Next.js version with breaking API changes from what training data assumes — check `node_modules/next/dist/docs/` before writing frontend code that touches Next.js APIs/conventions.

## Core Rules

- `PlanningState` is the source of truth; render the frontend from it, don't invent client-side.
- Providers supply facts, AI supplies reasoning/explanation only — never let AI invent a price, rating, availability, route, or booking link. Never fabricate mock hotels/restaurants/prices/ratings/routes as product data.
- Do not scrape restricted providers (Airbnb, Booking.com, Expedia, Vrbo, Tripadvisor, Google Flights).
- If data is unavailable, mark it `unavailable`; if a provider isn't connected, mark it `not_connected` — never silently omit or guess.
- Validation must run before a plan is shown as final; user locks must be respected — an active lock blocks regeneration entirely rather than being worked around; feedback-driven regeneration (Section 174) updates only the affected section(s) it can derive, and only when it can.
- Work in small steps; don't rewrite the staged architecture or bundle large unrelated changes. If unsure whether something is real product logic vs. placeholder, ask before implementing.
- Use `.env` for local secrets (never commit it); `.env.example` in the repo root documents every setting (names and safe defaults only) — keep it in sync with `backend/app/core/config.py` when adding one.

**Note on `.github/` instructions**: `.github/copilot-instructions.md` and `.github/instructions/*.md` describe an earlier, looser design (mock providers, mock data allowed if labeled) that predates and conflicts with the no-mock-data policy above, which is what's actually enforced in code today. Treat this file as authoritative over those.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TravelObligator is an AI travel **decision** platform, not a one-shot itinerary generator. The product is the staged decision pipeline that produces and explains a plan, not just the plan itself:

```text
Traveler Profile → Destination Context → Trip Strategy → Stay + Transport
  → Experience Planner → Plan Validator → Feedback Pipeline → Final Itinerary
```

Two services: a FastAPI/Python backend (`backend/`) and a Next.js/React frontend (`frontend/`), backed by PostgreSQL by default (Section 200A; an explicit Local JSON fallback exists for dev/test — see Architecture below).

Read `docs/00_product_vision.md` and `docs/09_planning_state.md` first if you haven't touched this repo before. Full recommended reading order (`docs/00`–`docs/18`, `docs/20`) is in `README.md`.

## Commands

**Backend** (from `backend/`, or via Docker):
```bash
pip install -r requirements.txt -r requirements-dev.txt   # requirements-dev adds pytest
uvicorn app.main:app --reload                              # dev server, port 8000
```

**Tests** (from repo root — `pytest.ini` sets `pythonpath=backend`, `testpaths=backend/app/tests`):
```bash
pytest                                                      # full backend suite
pytest backend/app/tests/services/test_feedback_service.py  # one file
pytest backend/app/tests/services/test_feedback_service.py::test_name  # one test
python -m compileall backend/app                            # compile check (CI also runs this)
```
There is no backend lint/type-check config (no ruff/mypy) in this repo.

**Frontend** (from `frontend/`):
```bash
npm run dev      # dev server, port 3000
npm run build    # next build
npm run lint     # eslint; CI also runs `npx tsc --noEmit` and the build
npm test         # Node's built-in test runner over frontend/tests/*.test.mjs (no test framework dependency)
```

**Full stack**: `docker compose up --build` (root `docker-compose.yml`, Section 200E) is a production-style stack from the real images: `postgres` → one-shot `migrate` (`alembic upgrade head`; the backend never migrates) → `backend` (one Uvicorn worker, read-only root, `127.0.0.1:8000`) → `frontend` (Next standalone, `127.0.0.1:3000`), plus a `redis` cache-only, DISPOSABLE container that is NOT a backend startup dependency (the backend must start degraded without it; PostgreSQL + the migration are the only hard prerequisites); Postgres/Redis publish no host ports and require `POSTGRES_PASSWORD` + `SESSION_SECRET_KEY` from your environment (no defaults). The hot-reload dev workflow is `docker compose -f docker-compose.yml -f docker-compose.dev.yml up`.

CI (`.github/workflows/ci.yml`, Section 203A) runs five jobs on Python 3.11 / Node 22 / PostgreSQL 16 / Redis 7.4: `Backend / Hermetic` (`compileall` + plain `pytest`, no services), `Backend / Integration` (single Alembic head, `alembic upgrade head` on an empty database, full suite with both gates, zero skips enforced), `Frontend / Build` (`npm ci`, `tsc --noEmit`, lint, build), `Containers / Build & Smoke` (production images, `scripts/ci/image_audit.sh`, Trivy image gate, `scripts/ci/container_smoke.sh`) and `Security / Scan` (Trivy secrets + dependencies). Job names are branch-protection check names — don't rename them. No deploy step, no registry push, no secret.

## Architecture

**`PlanningState` is the single source of truth.** It's one Pydantic model (`backend/app/models/planning_state.py`) holding every section of a trip's plan (traveler profile, destination context, trip strategy, stay/transport, experience plan, validation report, feedback history, locks, version history, provider coverage, etc.). Each section is owned by exactly one backend stage service; the frontend renders directly from it and invents nothing itself.

**Backend layering** (`API → Orchestrator/Services → ProviderGateway/Repositories/Validators → Provider Adapters/Database`):
- `backend/app/api/routes/trips.py` — the single router (prefix `/trips`). Every response is wrapped in a standard envelope (`success`, `data`, `message`, `errors`, `metadata`) built in `core/response.py`; business errors are `AppError` subclasses from `core/errors.py`, converted to that envelope by a handler in `main.py`.
- `backend/app/services/planning_orchestrator.py` — `PlanningOrchestrator.generate_full_plan()` runs the 6 core stage services in a fixed order inside `POST /trips/{id}/generate`, saving `PlanningState` to the repository after every stage. This is the main write path; it's a single synchronous request (no job queue).
- Stage services (`backend/app/services/{traveler_profile,destination_context,trip_strategy,stay_transport,experience_planner,plan_validator}_service.py`) each own specific `PlanningState` fields and must not touch fields owned by another stage.
- `backend/app/providers/gateway.py` (`ProviderGateway`) is the *only* way stage services reach external data — never import a provider adapter directly. Real adapters exist for places (OpenStreetMap/Overpass for POI discovery; destination geocoding and named-place search go through a separate `GeocodingProvider` in `app/providers/geocoding/` selected by `GEOCODING_PROVIDER` — `nominatim` default for dev/tests, paced to 1 req/s with a 429 cooldown; `geoapify` in production, needs `GEOAPIFY_API_KEY`; no fallback between them, and `APP_ENV=production` rejects the public Nominatim endpoint — Section 203C.1), weather (Open-Meteo), holidays (Nager.Date), currency (Frankfurter), routing (OSRM — `ROUTING_PROVIDER` default `not_connected`, `osrm` when explicitly configured), and accommodation/flights (`scraped_local` — a local/manual static-HTML parser, enabled by default but honestly `unavailable` with no file present at `SCRAPED_ACCOMMODATION_HTML_PATH`/`SCRAPED_FLIGHT_HTML_PATH`). Flights additionally has a real, live third-party adapter (Kiwi via MCP — `FLIGHT_PROVIDER=kiwi_mcp` + `KIWI_MCP_ENABLED=true`, both required, default off). Transit still has no adapter and always reports `not_connected`. Hotel ratings (`HOTEL_RATINGS_PROVIDER`) has a provider slot but no live rating source wired in yet, defaulting to `not_connected`.
- `backend/app/repositories/` — **Section 200A: PostgreSQL is the default persistence backend.** `Settings.persistence_backend` (`PERSISTENCE_BACKEND`, default `postgres`) is the one selector; `app/repositories/factory.py` (`get_*_repository()`) returns Postgres repositories for users, trips, planning states, jobs and branches/revisions (SQLAlchemy/psycopg, Alembic migrations run as a release step, never automatically). `DATABASE_URL` is required (no default); missing/invalid/unreachable/un-migrated Postgres stops startup with a credential-free message and **never falls back to Local JSON**. `PERSISTENCE_BACKEND=local_json` is an explicit dev/test fallback (`LocalJsonStore` → gitignored `backend/.data/travelobligator_state.json`); hermetic pytest selects it explicitly in `conftest.py`. Never bind a Local JSON repository singleton directly in a service — always resolve through the factory.
- **Containers and runtime (Section 200E).** `docker compose up --build` is a production-STYLE stack from the real images (`postgres` → one-shot `migrate` → `backend` → `frontend`, plus `redis`); `docker-compose.dev.yml` is the old hot-reload workflow. Backend: multi-stage `python:3.11.16-slim-bookworm`, non-root uid 10001, exec-form `python -m app.serve` = **exactly ONE Uvicorn worker per container** (metrics/heartbeats are process-local; scale by containers), read-only root + tmpfs in PostgreSQL+Redis mode. **Migrations are an explicit step, never run by the web process** (the backend only verifies the head and refuses to start on a mismatch). DB pool/timeouts are settings (`DB_POOL_SIZE`+`DB_MAX_OVERFLOW` = max connections per container; `DB_STATEMENT_TIMEOUT_MS`/`DB_LOCK_TIMEOUT_MS` apply to request traffic, not migrations). Graceful SIGTERM closes this process's own in-flight jobs as `JOB_INTERRUPTED` (lease-conditional) and exits; a hard kill relies on lease expiry. Postgres/Redis publish NO host ports (dev override: 127.0.0.1 only); `/health` is the container liveness check, `/ready` is for traffic routing, `/ready`+`/metrics` need private routing in production. Frontend: Next `output: "standalone"`, Node 22, non-root; the browser's API URL is the RUNTIME `API_BASE_URL` (never an internal service name). Async jobs are `BackgroundTasks` + leases, **not a durable queue**. Details: `docs/14_backend_architecture.md` section 164.
- **Health, readiness, observability (Section 200D).** `/health` is liveness ONLY (no dependency call, no config dump); `/ready` (`core/readiness.py`) = PostgreSQL reachable + schema at the code's Alembic head (else 503 `not_ready`), Redis down = `degraded` (200), Redis disabled reported as such, external travel/AI providers are NEVER called by readiness. Probes are bounded (`READINESS_TIMEOUT_SECONDS`, dedicated one-connection engine, `DB_CONNECT_TIMEOUT_SECONDS`) and recover without a restart. Metrics: `core/metrics.py` (dependency-free registry, Prometheus text at `/metrics`, `METRICS_ENABLED`); **never label a metric with a trip/job/user/revision id, destination, free text, URL or request id** (HTTP uses route TEMPLATES). Logging: use the existing allowlisted structured pipeline + `core/ops_events.py` names; every line is passed through `core/redaction.py`; never log feedback text, itinerary/narrative text, prompts, provider payloads, tokens or URLs. `validate_runtime_configuration` rejects contradictions at startup (e.g. job max > 1 with PostgreSQL). Heartbeat threads are registered and stopped at shutdown. Details: `docs/14_backend_architecture.md` section 163.
- **Transactions and concurrency (Section 200C).** PostgreSQL is authoritative and does the concurrency control; Redis is never a lock. Use `app/repositories/unit_of_work.py` (`unit_of_work()` / `run_atomic`) for multi-write transitions: repositories bound to its one session never commit themselves; **never call a provider/AI/Redis inside a unit of work** (compute first, then a short transaction). `PlanningState` writes are optimistic: `planning_states.lock_version` compare-and-set via a private `_lock_version` token (stale writer → `ConcurrentStateUpdateError` → HTTP 409 `CONCURRENT_UPDATE`; an unread object may only INSERT). State + revision + branch head commit together through `RevisionLineageService.commit_state_with_revision` — never pair `save()` with `record_current_revision()`. Branch activation locks the state row; branch heads use compare-and-set. Jobs: a partial unique index allows one queued/running job per trip; running jobs are owned by a DB lease (`claim`/`heartbeat`/`transition`, `GENERATION_JOB_LEASE_SECONDS`); terminal transitions are conditional and idempotent; startup recovery only closes expired leases. Isolation is READ COMMITTED (not SERIALIZABLE); only 40001/40P01 are retried (3 attempts). Local JSON stays an explicit dev backend **without** these guarantees. Not exactly-once distributed execution. Details: `docs/14_backend_architecture.md` section 162.
- **Provider-response cache (Section 200B).** `PROVIDER_CACHE_BACKEND` (default `redis`; `sqlite` is the explicit local-dev alternative; `PROVIDER_CACHE_ENABLED=false` is the kill switch) picks the backend inside `get_provider_cache_store` (`app/storage/provider_cache_store.py`); the Redis implementation is `app/storage/redis_provider_cache_store.py` (keys `<prefix>:provider-cache:v1:<provider>:<sha256>`, JSON envelope, volatility-based TTLs, bump `CACHE_NAMESPACE_VERSION` to invalidate). **Redis is an optimization, never authoritative:** if it is down, provider calls simply run uncached — never a hidden SQLite fallback, never a fabricated value, never a failed request. A malformed `REDIS_URL` stops startup; an unreachable one only degrades. Never cache AI/LLM output or transient provider failures; scraped/local-file caches stay off Redis. Ordinary `pytest` selects `sqlite` explicitly and needs no Redis; real-Redis tests are gated (`TRAVELOB_RUN_REDIS_TESTS=1` + `REDIS_URL`, marker `redis_integration`). Details: `docs/14_backend_architecture.md` section 161.
- **Free-tier deployment contract (Section 203B; nothing is deployed yet).** Target: Vercel (frontend) → same-origin `/api/*` rewrite → Render free Docker web service → Neon PostgreSQL + Upstash Redis. The rewrite exists only when `BACKEND_ORIGIN` is set at frontend build time (`frontend/next.config.ts`; pair with runtime `API_BASE_URL=/api`); local dev, Docker and CI leave it unset. `APP_ENV=production` turns on strict startup validation in `core/operational_config.py` (PostgreSQL only, no SQLite provider cache, `APP_DEBUG=false`, Secure/HttpOnly/non-`none` session cookie, ≥32-char `SESSION_SECRET_KEY`, https-only explicit CORS origins); a wildcard or credentialed CORS origin is rejected in every environment. Every backend response is `Cache-Control: no-store` (`core/no_store_middleware.py`). `/health` is always public; `/ready` and `/metrics` require `Authorization: Bearer <OPS_TOKEN>` when `OPS_TOKEN` is set, are 404 in production without it, and stay open otherwise (Compose/CI). `render.yaml` is one free web service with no secret values; migrations stay a manual step before each deploy. No keepalive/cron ping to defeat free-tier sleep. Details and the 203C checklist: `docs/22_free_tier_deployment.md`.
- **Final V1 itinerary engine (Section 203C.2B).** Production topology: Geoapify Geocoding (destination + named-place grounding) → Geoapify Places (`PLACES_PROVIDER=geoapify`, `providers/places/geoapify_places_adapter.py`: broad factual pool inside the destination boundary, category identifiers only from the verified snapshot in `geoapify_categories.py`) → Groq anchor proposals (hypotheses only; every one is grounded through the geocoder before it is eligible, and a grounded place already in the pool keeps the pool identity) → candidate quality → inventory sufficiency gate → reasoning → Geoapify Routing (`ROUTING_PROVIDER=geoapify`) → validation → narrator. **Overpass is development-only** (`PLACES_PROVIDER=openstreetmap`, rejected with `APP_ENV=production`); never add a fallback between providers. **Provider result order is never a prominence signal.** `T = days × pace target (2/3/4)`, `R = ceil(0.8·T)`, `H = ceil(2.25·T)` live in `services/pace_targets.py`; `services/usefulness_contract.py` owns the semantics: `viable ≥ H` healthy, `≥ T` sufficient, `≥ R` thin-but-usable, `< R` insufficient. Whenever `viable ≥ R` a plan needs ≥ R meaningful stops and no empty day (one AI repair, then one deterministic top-up, then `UNDERFILLED_PLAN` / needs_review). **Only `viable < R` is `INSUFFICIENT_VERIFIED_INVENTORY`, and that is a completed generation with `readiness=blocked` (job `succeeded`, state persisted) — never an `AppError` or a failed job, and never padded.** Routing is bounded and non-quadratic: one multi-waypoint request per day, at most one alternative order per day (chosen by `services/day_order_heuristics.py`; the routing services themselves never compute straight-line distance), no pair matrix. **Provider credits are accounted per generation** through an explicit `GenerationProviderContext` (`core/provider_usage.py`) passed from each entry point into `gateway.places_for(ctx)` / `routing_for(ctx)` / `get_route_sequence(..., ctx)` — never a process-global counter; adapters reserve before a request, settle after, and refuse locally past `GEOAPIFY_MAX_CREDITS_PER_GENERATION`. Every Geoapify call goes through `providers/geoapify_client.py` (generic `ProviderRequestError`; `GeocoderError` is only its geocoder-worded subclass). The hermetic suite turns the gate off for its tiny legacy fixtures (`INVENTORY_SUFFICIENCY_GATE_ENABLED=false` in `conftest.py`); opt in with the `inventory_sufficiency_gate_enabled` fixture. Benchmark data (`backend/scripts/benchmark/`) is never imported by `backend/app`, and no city or landmark name belongs in production logic. Details: `docs/22_free_tier_deployment.md`.
- No authentication/authorization exists anywhere; every endpoint is scoped only by knowledge of a `trip_id`.
- Services, the orchestrator, and the gateway are constructed as module-level singletons at import time, not via FastAPI `Depends()` — tests override behavior by monkeypatching these singletons directly (see `backend/app/tests/conftest.py`).

**Regeneration is implemented, but MVP-scoped and refusal-first.** `POST /trips/{id}/regenerate` (Section 174) mutates the plan only when `confirm: true`, at least one feedback event is still pending, zero locks are active, and a real affected stage is derivable from that feedback — in that case it reruns exactly those stages via `PlanningOrchestrator.rerun_affected_stages`, creates a new `VersionHistoryItem`, and marks the feedback events applied. Every other case (missing/false `confirm`, any active lock, no pending feedback, or no derivable affected stage) is a distinct, named refusal (`REGENERATION_NOT_AVAILABLE` / `REGENERATION_BLOCKED_BY_LOCKS` / `REGENERATION_NO_PENDING_FEEDBACK`) that appends an audit attempt and changes nothing. An active lock always blocks regeneration outright — the system never works around a lock, merges past it, or "preserves" it by excluding just that item; a locked plan must be unlocked first. A successful regeneration is never a claim that the plan improved, and never a claim it is now ready for real-world use without further review. `POST /trips/{id}/feedback` still only classifies feedback with deterministic keyword rules (no AI, no plan mutation itself) — `POST /trips/{id}/regenerate` is the endpoint that can act on it. Before touching any regeneration-adjacent code, read `docs/17_regeneration_manual_qa.md` and run its checklist — every refusal path above is a safety contract, not a placeholder to "finish." **Section 202B.1 (honest semantics):** the legacy (non-targeted) path only reruns deterministic stages over the same `trip_request` — no stage reads feedback text — so it can no longer claim a free-text request was applied. Legacy regeneration now runs only for a `feedback_type` with a registered deterministic operation *and* a postcondition proving the effect (`LEGACY_SUPPORTED_OPERATIONS` in `regeneration_mutation_service.py`, intentionally empty); otherwise it refuses with `REGENERATION_FEEDBACK_NOT_INTERPRETABLE` (no rerun, no version, feedback stays pending). Free-text changes need the targeted AI path (`TARGETED_REGENERATION_ENABLED=true` + AI feedback interpreter). A targeted result that changes nothing is `REGENERATION_NO_EFFECT` (no version); reported affected/preserved days are derived from the final states, never from plan metadata; AI provider failures are classified (`app/providers/ai_failure.py`) into `REGENERATION_PROVIDER_RATE_LIMITED` / `REGENERATION_AI_UNAVAILABLE`, never the generic refusal. Provider-grounded experiences carry `provider_source`/`provider_place_id` and a deterministic `experience_id`, so unchanged places keep their id across regenerations and the same place is never scheduled twice.

**AI candidate-proposal subsystem** (`backend/app/providers/ai_candidate_proposal/`) is a separate, fully-built shadow-mode path (`AI_CANDIDATE_PROPOSAL_PROVIDER` default `not_connected`; `anthropic` is the primary wired LLM base, `groq` a cheaper/dev-only alternative — neither is a factual data source, both propose candidates only, forced tool-use schema that structurally forbids factual fields like price/rating/coordinates) gated by `AI_CANDIDATE_DISCOVERY_SHADOW_MODE_ENABLED` (default off). When enabled it populates `ai_candidate_proposal_batch`/`candidate_grounding_batch` for inspection only — it never feeds scheduling, `validation_report`, or `provider_coverage`. Don't wire it into the real pipeline unless explicitly asked to.

**Frontend** is a single route (`frontend/app/page.tsx`, one large file — no `components/`/`hooks/`/dynamic routing). `frontend/lib/api.ts` is a thin fetch client, one function per backend endpoint; `frontend/lib/types.ts` is a hand-maintained partial mirror of backend response shapes (not generated — keep both in sync manually when changing API contracts). State is plain `useState`, no store library. Loading a trip fires `GET /summary` then 7 parallel calls assembled client-side into one `PlanResult` — this deviates from `docs/16_frontend_architecture.md`'s single-fetch design; that's a known, accepted divergence, not a bug to silently "fix."

**Next.js version note**: `frontend/AGENTS.md` (pulled in via `frontend/CLAUDE.md`) warns this is a bleeding-edge Next.js version with breaking API changes from what training data assumes — check `node_modules/next/dist/docs/` before writing frontend code that touches Next.js APIs/conventions.

For a full file-by-file map, traced request/response flows with file:line references, and a list of known gaps, see `docs/CODEBASE_OVERVIEW.md`.

## Core Rules

- `PlanningState` is the source of truth; render the frontend from it, don't invent client-side.
- Providers supply facts, AI supplies reasoning/explanation only — never let AI invent a price, rating, availability, route, or booking link. Never fabricate mock hotels/restaurants/prices/ratings/routes as product data.
- Do not scrape restricted providers (Airbnb, Booking.com, Expedia, Vrbo, Tripadvisor, Google Flights).
- If data is unavailable, mark it `unavailable`; if a provider isn't connected, mark it `not_connected` — never silently omit or guess.
- Validation must run before a plan is shown as final; user locks must be respected — an active lock blocks regeneration entirely rather than being worked around; feedback-driven regeneration (Section 174) updates only the affected section(s) it can derive, and only when it can.
- Work in small steps; don't rewrite the staged architecture or bundle large unrelated changes. If unsure whether something is real product logic vs. placeholder, ask before implementing.
- Use `.env` for local secrets (never commit it); there is currently no `.env.example` in the repo despite this being the intended pattern — reconstruct the expected variable list from `backend/app/core/config.py` if you need to add one.

**Note on `.github/` instructions**: `.github/copilot-instructions.md` and `.github/instructions/*.md` describe an earlier, looser design (mock providers, mock data allowed if labeled) that predates and conflicts with the no-mock-data policy above, which is what's actually enforced in code today. Treat this file as authoritative over those.

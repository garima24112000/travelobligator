# 28. Beta readiness assessment (Phase 3)

Written after Phases 1 and 2 (commits `d9030b9`, `efa1546`) for the project owner and reviewers. It records
what is verified, what is not, the itinerary-quality limitations that remain, and how a future quality
decision has to be reached. It changes no threshold, no score and no part of the quality contract
(`docs/24_itinerary_quality_contract.md`).

## 1. The quality result stands

The V1 manual quality acceptance **failed** and that result is final for the frozen holdout
(`docs/27_v1_quality_acceptance_report.md`): median Overall 2/5 against a target of ≥ 4, and eight of ten
itineraries below 3. The holdout (`benchmark_results/quality_holdout_v1/`, 21 files) and the signed scores
(`docs/26_quality_holdout_manual_review.md`) are frozen. Phases 1–3 improved disclosures and reliability;
**no evidence since shows the quality target is met, and none of this work may be presented as if it were.**
The quality gate is **NOT MET** until a new, unseen acceptance set (section 5) is run and scored.

The release target is unchanged, quoted from `docs/24_itinerary_quality_contract.md` section 6:

> **Release target, on the final unseen quality holdout:**
> - median overall score ≥ 4 of 5;
> - no scenario with an overall score below 3;
> - zero hard factual-safety failures (part A).

## 5. Independent evaluation plan

Three sets are kept apart, and their roles never change:

| Set | Where | Role |
| --- | --- | --- |
| Development / tuning | `quality_tuning` (Q-T1…Q-T6) in `backend/scripts/benchmark/quality_v1.json`; `cities.json` | May be run and rerun while working; never evidence for release |
| Historical exposed holdout | `quality_holdout` (Q-H1…Q-H10), results in `benchmark_results/quality_holdout_v1/` | Frozen and **exposed** (its failures shaped later work). Never rerun, edited or rescored |
| New unseen acceptance | not yet created | The only set whose result can change the quality decision |

Procedure for the new acceptance set. Each step needs the owner's approval where marked; nothing here has
been run.

1. **Define (owner approval).** Ten or more scenarios in a new file (e.g.
   `backend/scripts/benchmark/quality_v2.json`, set `quality-acceptance-v2`), with destinations, trip
   lengths, paces, interests and must-visits **not** used in any tuning or holdout scenario, and chosen to
   cover the contract's categories (food, waterfront, must-visits, multi-day geography). Nobody who tuned
   the planner may see the generated plans before scoring.
2. **Freeze.** Pin the file by SHA-256 in a test, as `test_benchmark_quality_q0.py` pins the holdout; give
   the set the same run-once guard (`--allow-…`, whole set only, no `--scenarios`).
3. **Budget (owner approval).** Each generation is capped at `GEOAPIFY_MAX_CREDITS_PER_GENERATION` = 100
   Geoapify credits; the frozen holdout used 37–67 per scenario (mean about 51). Model stages: 3–4 per
   scenario, each at most two requests. Ten scenarios: at most 1,000 credits and 80 model requests.
4. **Run once** from a clean tree at one recorded commit, with the provenance the benchmark already writes
   (source fingerprint, configuration hash, `source_unchanged_during_scenario`). An interrupted run is
   resumed, never restarted.
5. **Fingerprint** every output file (SHA-256) before anyone reads a plan.
6. **Score** with the contract's Part C rubric by a reviewer who did not tune the planner, unaware of the
   automated verdicts, with place facts checked and attributed as in doc 26.
7. **Decide** against the contract's own, unchanged release target. Record the result next to doc 27; the
   old holdout result is not replaced.

No human score is assigned in advance, and none is implied by this plan.

## 6. E2E reliability findings (Phase 3)

| Symptom | Finding | Status |
| --- | --- | --- |
| A generation job ends `failed` in the browser tests (`saved-trips.spec.ts:112`, `:185`) | The offline E2E backend uses the Local JSON development store. Its repositories serialised each collection by iterating the LIVE in-memory dict; a concurrent insert from another request thread raised "dictionary changed size during iteration", which fails the job. Reproduced with forced thread switches: 3 errors in one run of 490 concurrent writes before the fix, 0 in three runs after. Eleven READ paths ("My trips", jobs of a trip, branch / revision lookups, sign-in by email) had the same defect (6–8 errors per forced run before, 0 after) | **Fixed** (every write and read iterates a snapshot, in five Local JSON repositories; regression tests fail without the fix). Production (PostgreSQL) never used this code |
| Remaining Local JSON risk (not fixed) | A write takes its snapshot before entering the store's lock, so two concurrent writes can reach the file in the opposite order: the file can lag the in-memory data by one write until the next write. The file is never corrupt or partly written (temporary file, fsync, atomic replace, under the lock) and the running process always reads its complete in-memory copy; only a restart inside that window could lose the latest record. Each repository is one module-level instance, so no two in-memory copies overwrite each other | **Documented, development store only** — not a full concurrency guarantee; the store already states it makes none |
| Backend errors were not kept | The harness discarded the backend's stdout, where the structured log (and a failed job's traceback) is written | **Fixed**: `frontend/e2e-results/backend.log` (fixture data only, redacted by the application's own pipeline — checked: no password, cookie, token or email; synthetic account and request ids are written — mode 600; if it cannot be opened the backend runs without it). It is in the CI artifact `browser-e2e-results`: 14-day retention, and the repository is public, so any signed-in GitHub user can download it |
| The failure said only `failed` | `generateViaApi` polled the status alone | **Fixed**: a failing wait now also prints the job's last status, error code and fixed error message |
| `auth.spec.ts` "wrong credentials …" timed out waiting for the sign-in form (local, once, during the Phase 3 audit) | The new backend log showed the logout succeeding 51 ms after the test's sign-up; the page was still signed in. Sessions are signed cookies, so logging out depends on the browser applying the response's cookie-clearing `Set-Cookie`; the test navigated immediately after clicking Log out, which can cancel the response first. Every other test that logs out waits for the signed-out screen | **Fixed in the test** (it now waits for the signed-out screen like the others); no assertion or timeout loosened. The application was not at fault |
| ECONNRESET on `POST /trips` through the frontend proxy (CI, once) | Both the backend (uvicorn) and Node's HTTP agent keep idle connections for 5 s, so a reuse-at-close race is possible. A targeted probe (30 requests through the production proxy after idle gaps of 4.85–5.14 s) did not reproduce it | **Unresolved, unproven** — nothing changed; the new backend log will show the backend's side if it recurs |

No assertion, timeout or retry setting was changed; `retries: 0` stands.

## 7. Remaining itinerary-quality limitations

None of these is solved, and none may be described as solved.

| Limitation | What exists today | What a fix needs |
| --- | --- | --- |
| Closed or relocated venues | Every day says opening hours and feasibility are not checked; explicit private / no-access tags are filtered, and disclosed for must-visits (R2a) | An operational-status source; the recorded Places response holds no lifecycle tag |
| Opening hours, tickets, visit length | Disclosed in general, never checked | An hours / admission source (new provider) |
| Low-value filler | One usefulness ordering; most stops are chosen by the reasoning model | A provider-backed significance signal, or a contract decision on filling to T |
| Same-venue duplication | Same-place and tagged sub-feature duplicates are caught; containment (a chapel inside a castle) is not | Containment geometry or relations from the provider (Place Details cost) |
| Food experiences | Food met only by nearby suggestions is now disclosed as such (Phase 2) | A verified food-court / food-market category (needs a probe) |
| Waterfront classification | Piers, beaches and marinas only; "no supply" wording now says what the place data identifies (Phase 2) | Water geometry or a verified category; names and proximity are not evidence |
| Must-visit grounding failures | An ungrounded must-visit is disclosed (`MUST_VISIT`) | One live geocoder lookup to find why a known landmark was not matched |
| Unverified transport modes | Over-limit walks are named and marked; ferries only when the provider says so; transit `not_connected` | A transit provider |
| Driving allowance across planner passes | Longest-walk-first within a pass (R1) | A budget decision: earlier passes still consume the allowance |
| Remote-day heuristic | Disclosed with the planner's own pool-reach boundary (Phase 1) | Development cases with real geography; it may flag legitimate outer districts |
| Must-visit with repeated route refusals | The neighbour is no longer replaced in vain (Phase 1); the leg is disclosed | Nothing proves why the provider refuses; never inferred |
